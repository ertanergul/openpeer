## 1. Full ERD

Principle: the ERD shows **relations + keys + status values**; exhaustive columns/limits remain in 0.4.

```mermaid
erDiagram
    users {
        bigint id PK "starter auto-increment"
        boolean is_admin "default false"
    }
    expert_profiles {
        char26 id PK "ULID"
        bigint user_id FK "RESTRICT, UNIQUE one profile per user"
        varchar username UK "reserved paths validated in app"
        varchar timezone "IANA, not null"
        varchar status "draft or published"
        timestamptz published_at "null until published"
        jsonb languages "bounded ISO list"
    }
    categories {
        char26 id PK
        varchar slug UK
        boolean is_active "deactivate instead of delete"
        smallint sort_order
    }
    expert_categories {
        char26 id PK
        char26 expert_profile_id FK "CASCADE"
        char26 category_id FK "RESTRICT"
    }
    services {
        char26 id PK
        char26 expert_profile_id FK "CASCADE"
        varchar title
        smallint duration_minutes "CHECK 15-480"
        bigint price_minor "CHECK zero or more"
        char3 currency "ISO-4217"
        varchar meeting_provider "default manual"
        int buffer_before_minutes "default 0"
        int buffer_after_minutes "default 0"
        int min_booking_notice_minutes "default 0"
        int max_booking_horizon_days "default 60"
        int cancellation_cutoff_hours "nullable"
        smallint cancellation_refund_percent "nullable"
        boolean is_active "partial index WHERE is_active"
    }
    availability_rules {
        char26 id PK
        char26 expert_profile_id FK "CASCADE"
        smallint weekday "CHECK 1-7, Mon is 1"
        time start_time "expert TZ wall clock"
        time end_time "CHECK start before end"
    }
    availability_exceptions {
        char26 id PK
        char26 expert_profile_id FK "CASCADE"
        date exception_date
        varchar type "day_off, blocked, unavailable"
        time start_time "null means whole day"
        time end_time
    }
    booking_holds {
        char26 id PK
        char26 expert_profile_id FK "RESTRICT"
        char26 service_id FK "RESTRICT"
        bigint customer_user_id FK "RESTRICT"

        timestamptz ends_at
        timestamptz expires_at "read-time expiry"
        varchar status "active, consumed, released, expired"

    bookings {
        char26 id PK
        char26 hold_id FK "RESTRICT not null, UNIQUE one hold per booking"
        bigint customer_id FK "RESTRICT"
        char26 expert_profile_id FK "RESTRICT"

        varchar service_title "purchase-time snapshot"
        smallint duration_minutes "snapshot"
        bigint price_minor "snapshot"
        char3 price_currency "snapshot"

        timestamptz ends_at
        varchar customer_timezone
        varchar status "pending_payment, confirmed, completed, cancelled, expired, payment_failed"
        varchar cancelled_by "system, customer, expert, admin"
        timestamptz cancelled_at "nullable"
    }
    payments {
        char26 id PK
        char26 booking_id FK "RESTRICT, one row per attempt"
        varchar gateway
        varchar provider_reference "partial UNIQUE with gateway"
        bigint amount_minor "CHECK zero or more"
        char3 currency
        varchar status "pending, requires_action, succeeded, failed, refunded, partially_refunded"
        varchar idempotency_key "partial UNIQUE"
        jsonb metadata "never card data"
    }
    refunds {
        char26 id PK
        char26 payment_id FK "RESTRICT"
        bigint amount_minor "CHECK > 0"
        char3 currency "equals payment currency"
        varchar status "pending, succeeded, failed, rejected"
        varchar provider_reference "partial UNIQUE"
        timestamptz processed_at "nullable"
    }
    webhook_events {
        char26 id PK
        varchar gateway
        varchar external_event_id "UNIQUE with gateway when present"
        varchar event_type
        jsonb payload
        boolean signature_valid "default false"
        varchar status "received, processed, ignored, failed"
        timestamptz processed_at "nullable"
    }
    financial_entries {
        char26 id PK
        char26 booking_id FK "RESTRICT"
        char26 payment_id FK "nullable"
        varchar entry_type "sale, platform_commission, provider_fee, expert_share, refund"
        bigint amount_minor "signed"
        char3 currency
        timestamptz occurred_at "immutable insert-only"
    }
    meeting_details {
        char26 id PK
        char26 booking_id FK "RESTRICT, UNIQUE one link per booking"
        varchar provider "manual MVP"
        text meeting_url "https, allow-listed hosts"
        bigint added_by_user_id FK "RESTRICT"
        timestamptz added_at
    }
    calendar_connections {
        char26 id PK
        bigint user_id FK "RESTRICT"
        varchar provider "reserved for P5"
        text encrypted_payload "Laravel encrypted cast, P5 reserved"
        varchar status "UNIQUE with user_id and provider"
    }
```

Framework-owned tables (`users` partially, `notifications`) are outside the ERD's relation graph; starter columns of `users` are trimmed for readability.

## 2. Constraint Map (what ERD cannot express)

| Constraint type | Table | Definition |
|---|---|---|
| Partial UNIQUE | `payments` | `(gateway, provider_reference) WHERE provider_reference IS NOT NULL` |
| Partial UNIQUE | `payments` | `(idempotency_key) WHERE idempotency_key IS NOT NULL` |
| Partial UNIQUE | `refunds` | `(gateway, provider_reference) WHERE provider_reference IS NOT NULL` |
| Partial UNIQUE | `bookings` | `(hold_id)` — one hold produces at most one booking |
| UNIQUE | `expert_profiles` | `username`, plus `user_id` (single profile per user) |
| UNIQUE (composite) | `availability_rules` | `(expert_profile_id, weekday, start_time, end_time)` |
| UNIQUE (expression) | `availability_exceptions` | `(expert_profile_id, exception_date, COALESCE(start_time,'00:00'), COALESCE(end_time,'23:59:59'))` |
| UNIQUE (composite) | `expert_categories` | `(expert_profile_id, category_id)` |
| UNIQUE | `meeting_details` | `(booking_id)` |
| UNIQUE | `calendar_connections` | `(user_id, provider)` |
| **EXCLUDE (gist)** | `booking_holds` | `(expert_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE status='active'` — active holds cannot overlap |
| **EXCLUDE (gist)** | `bookings` | `(expert_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE status IN ('confirmed','completed')` — confirmed overlaps impossible at DB level |
| CHECK | all touched tables | Domains/ranges as recorded column-by-column in 0.4 |
| Partial INDEX | public queries | `services WHERE is_active`; `expert_profiles WHERE status='published'`; `bookings` pending scan; webhook retry scan; hold expiry scan |

## 3. Acceptance Criteria

- ✅ Every FK from the approved 0.4 schema is represented with matching cardinalities (1-1 pairs: `users`↔`expert_profiles` via UNIQUE, `bookings`↔`meeting_details`, hold↔booking via UNIQUE).
- ✅ Reserved (`calendar_connections`) and framework tables separated clearly.
- ✅ Everything ERD syntax cannot show is recorded in the constraint map (§2).
- ✅ Standard Mermaid v10+ `erDiagram`; renders via mermaid.live or IDE preview; will be embedded into docs during Phase 1.6 for a permanent, CI-friendly rendering check.
