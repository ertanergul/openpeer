## 3. Decision Details (flagged + critical)

### D-01 — PHP version strategy
- **Decision:** left `{"php": "^8.3"}` untouched; target production runtime PHP 8.4; ban heretofore-8.4-only syntax until dev+CI uniformly run 8.4.
- **Alternatives:** upgrade local runtime now; pin `^8.4`.
- **Rationale:** runtime verified 8.3.35; `^8.3` is Laravel 13's official composer requirement and covers both; zero action required now and no env churn during Foundation.
- **Applied:** immediately (no change); revisit if CI standardizes on 8.4.

### D-03 — Database version
- **Decision:** PostgreSQL as primary from Phase 1.2; Docker image `postgres:17`.
- **Alternatives:** PG 16; PG 18.
- **Rationale:** 17 is broadly hostable by self-hosted community installs, with a mature `btree_gist` ecosystem (candidate dependency for time-range exclusion constraints) and long-supported `tstzrange`/GiST; the MVP needs no PG-18-only features.
- **Applied:** task 1.2 (env + migration verification) and 1.3 (compose service).

### D-05 — Dev environment drivers
- **Decision:** keep starter `database` drivers for session/cache; enforce `QUEUE_CONNECTION=sync`; keep mail `log`.
- **Alternatives:** master prompt's `file`/`sync`/`file`; database queue.
- **Rationale:** the prompt states those defaults as permissible ("can be used"), not mandated; `database` drivers satisfy the "no Redis" rule and need no extra service; a `database` queue **without a worker** would park jobs forever — the exact failure we must avoid before the Phase 5 queue decision.
- **Applied:** task 1.2 environment configuration.

### D-06 — Docker approach
- **Decision:** generate Docker tooling from the already-installed `laravel/sail` (dev dep, v1.69.0), trimmed to app + postgres services only.
- **Alternatives:** hand-written `Dockerfile` + `docker-compose.yml`.
- **Rationale:** the prompt's Foundation asks for exactly app + postgres; Sail is an official, maintained toolkit standard for Laravel OSS; hand-written infra is unmaintained surface area.
- **Consequence:** final scope evidence recorded in task 1.3 (no Redis, no workers, no extra services).

### D-08 — ID strategy
- **Decision:** bigint PKs preserved for framework/starter tables; **ULID PKs for new domain tables** (bookings, payment, holds, services, profiles, etc.); foreign keys from domain tables reference `users.id` (bigint); public exposure via slugs and opaque ULIDs only.
- **Alternatives:** UUIDv4 everywhere (random ordering → PostgreSQL index fragmentation); dual-column design (bigint PK + separate `public_id`) — more moving parts.
- **Rationale:** ULIDs (`HasUlids`) are native to Laravel, lexicographically sortable → good index locality in PostgreSQL, 26-character URL-friendly strings, zero custom code; protects against ID guessing for un-exposed URLs via opaque references.
- **Revisit trigger:** recorded — if future API or index-bloat evidence shows ulid overhead matters on hot tables, revisit with benchmarks; do not pre-adopt additional columns.
- **Applied:** Phase 1.2 / subsequent domain migrations.
