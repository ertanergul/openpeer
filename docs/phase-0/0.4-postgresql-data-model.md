## 3. Table Specifications

Convention: every new domain table has `id` (ULID PK, char(26), generated via `HasUlids`) and `created_at`/`updated_at` (`timestamptz`); only distinct columns are listed below.

### 3.1 Identity

**`users`** — starter table remains; one addition `is_admin boolean default false` (source of the Admin gate; no role tables in MVP). Deletion: FK RESTRICT anchor — users are never hard-deleted in MVP.

### 3.2 Profiles / Discovery / Services

**`expert_profiles`**

- `user_id` bigint FK→users **RESTRICT**, **UNIQUE** (one profile per user account, MVP)
- `username` varchar **UNIQUE** — reserved path list validated at app layer (not DB)
- `display_name` varchar; `headline` varchar null; `bio` text null; `avatar_path` varchar null
- `languages` jsonb default `[]` (bounded ISO code list); `social_links` jsonb default `{}`
- `timezone` varchar **NOT NULL** (IANA; application default `UTC`)
- `status` varchar default `draft` **CHECK in ('draft','published')**
- `published_at` timestamptz null
- Indexes: partial `INDEX (status) WHERE status='published'` for public-page queries

**`categories`**

- `slug` varchar **UNIQUE**; `name` varchar; `description` text null
- `is_active` boolean default true; `sort_order` smallint
- No hard delete — categories are deactivated via `is_active=false`

**`expert_categories`** (owned by Profiles)

- `expert_profile_id` ULID FK→expert_profiles **CASCADE**
- `category_id` ULID FK→categories **RESTRICT**
- **UNIQUE (expert_profile_id, category_id)**; index `(category_id)` for browse-by-category

**`services`**

- `expert_profile_id` ULID FK→expert_profiles **CASCADE**
- `title` varchar; `description` text
- `duration_minutes` smallint **CHECK 15–480**
- `price_minor` bigint **CHECK >= 0**; `currency` char(3)
- `meeting_provider` varchar default `'manual'`
- `min_booking_notice_minutes` int default 0; `max_booking_horizon_days` int default 60
- `buffer_before_minutes` int default 0; `buffer_after_minutes` int default 0
- `cancellation_cutoff_hours` int null; `cancellation_refund_percent` smallint null (simple MVP policy fields)
- `is_active` boolean default false
- Indexes: `(expert_profile_id)`; partial `INDEX WHERE is_active` (public service listing)

### 3.3 Scheduling

**`availability_rules`** — weekly recurrence, expert-local wall clock

- `expert_profile_id` ULID FK→expert_profiles **CASCADE**
- `weekday` smallint **CHECK 1–7** (ISO: Mon=1)
- `start_time` time / `end_time` time **CHECK start < end** (over-midnight unsupported in MVP; multi-rows instead)
- **UNIQUE (expert_profile_id, weekday, start_time, end_time)**; index `(expert_profile_id, weekday)`

**`availability_exceptions`**

- `expert_profile_id` ULID FK→expert_profiles **CASCADE**
- `exception_date` date **NOT NULL**
- `type` varchar **CHECK in ('day_off','blocked','unavailable')**; `reason` varchar null
- `start_time` time null / `end_time` time null (null = applies to whole day)
- Index: `(expert_profile_id, exception_date)`
- Uniqueness: **expression-based UNIQUE INDEX** `(expert_profile_id, exception_date, COALESCE(start_time,'00:00'), COALESCE(end_time,'23:59:59'))` (Postgres expression index prevents duplicate rows despite NULLs)

**`booking_holds`** — heart of the concurrency engine (final mechanism decided in 0.6)

- `expert_profile_id` ULID FK→expert_profiles **RESTRICT**
- `service_id` ULID FK→services **RESTRICT** (duration/buffer context)
- `customer_user_id` bigint FK→users **RESTRICT**
- `starts_at` / `ends_at` timestamptz **CHECK start < end**
- `status` varchar **CHECK in ('active','consumed','released','expired')**
- `expires_at` timestamptz null (read-time expiry: `active AND expires_at > now())
- **Primary conflict layer (candidate — final in 0.6):** `EXCLUDE USING gist (expert_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status = 'active')` — requires `btree_gist`; the row-lock alternative is presented in 0.6
- Indexes: `(expert_profile_id, status, expires_at)` and partial `(status, expires_at) WHERE status='active'`
- Deletion: hold rows are never deleted — status transitions only

### 3.4 Bookings

**`bookings`**

- `customer_id` bigint FK→users **RESTRICT**
- `expert_profile_id` / `service_id` ULID FK→… **RESTRICT**
- `hold_id` ULID FK→booking_holds **RESTRICT NOT NULL** (every MVP booking passes a hold) — **UNIQUE (hold_id)** (one hold = one booking)
- **Purchase-time snapshots:** `service_title` varchar, `duration_minutes` smallint, `price_minor` bigint, `price_currency` char(3), `cancellation_cutoff_hours` int null, `cancellation_refund_percent` smallint null, `meeting_provider` varchar
- `starts_at` / `ends_at` timestamptz; `customer_timezone` varchar NOT NULL
- `status` varchar **CHECK in ('pending_payment','confirmed','cancelled','completed','expired','payment_failed')**
- `cancelled_at` timestamptz null; `cancelled_by` varchar **CHECK in ('system','customer','expert','admin')**; `cancelled_reason` text null
- **Second conflict layer (final in 0.6):** `EXCLUDE USING gist (expert_profile_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status IN ('confirmed','completed'))` — overlapping _confirmed_ bookings for the same expert are impossible at the DB level; holds alone are not trusted as the last line of defense
- Indexes: `(customer_id, starts_at)`, `(expert_profile_id, starts_at)`, `(status, starts_at)`, partial `(status='pending_payment', starts_at)` for the expiry sweep
- Deletion: **never deleted**; state transitions only (financial/legal audit trail)

### 3.5 Payments & Financial records

**`payments`** (one row = one attempt)

- `booking_id` ULID FK→bookings **RESTRICT**
- `gateway` varchar (driver name); `provider_reference` varchar null (provider intent/transaction id)
- `amount_minor` bigint **CHECK >= 0**; `currency` char(3)
- `status` varchar **CHECK in ('pending','requires_action','succeeded','failed','refunded','partially_refunded')**
- `idempotency_key` varchar null; `metadata` jsonb default `'{}'`
- **No raw card data** — metadata must never contain card PAN (even under mock, synthetic values only)
- Partial **UNIQUE INDEX (gateway, provider_reference) WHERE provider_reference IS NOT NULL** (the same provider transaction cannot be recorded twice)
- Partial **UNIQUE (idempotency_key) WHERE idempotency_key IS NOT NULL**
- Indexes: `(booking_id, status)`; `(status, created_at)` for retry scans

**`refunds`**

- `payment_id` ULID FK→payments **RESTRICT**
- `amount_minor` bigint **CHECK > 0**; `currency` char(3) (equal to the payment's; enforced at app layer w/ FK)
- `status` varchar **CHECK in ('pending','succeeded','failed','rejected')**
- `provider_reference` varchar null; `reason` varchar null; `processed_at` timestamptz null
- Partial **UNIQUE (gateway, provider_reference) WHERE provider_reference IS NOT NULL** (idempotent refund)
- Index: `(payment_id, status)`

**`webhook_events`** (kept even for mock — idempotency architecture ships before the first real provider)

- `gateway` varchar; `external_event_id` varchar null (provider's event id); `event_type` varchar
- `payload` jsonb; `signature_valid` boolean default false
- `status` varchar **CHECK in ('received','processed','ignored','failed')**; `processed_at` timestamptz null; `failure_reason` text null
- **UNIQUE (gateway, external_event_id) WHERE external_event_id IS NOT NULL** — DB-level duplicate suppression; events without ids are deduped at the app layer
- Index: partial `(status) WHERE processed_at IS NULL` (retry scan)

**`financial_entries`** — **immutable** (insert-only; no updated_at)

- `booking_id` ULID FK→bookings **RESTRICT**; `payment_id` ULID FK→payments **RESTRICT null**
- `entry_type` varchar **CHECK in ('sale','platform_commission','provider_fee','expert_share','refund')**
- `amount_minor` bigint (signed: sale positive, commissions/fees/refunds negative)
- `currency` char(3) (single currency per booking in MVP)
- `occurred_at` timestamptz NOT NULL
- Indexes: `(booking_id)`, `(payment_id)`, `(entry_type, occurred_at)`

### 3.6 Meetings

**`meeting_details`**

- `booking_id` ULID FK→bookings **RESTRICT** — **UNIQUE (booking_id)** (one link row per booking)
- `provider` varchar default `'manual'` (MVP; future providers may add rows/types in the approved task)
- `meeting_url` text (validation: scheme `https` + allow-listed hosts)
- `added_by_user_id` bigint FK→users **RESTRICT**; `added_at` timestamptz
- Exposure rule from 0.3 stands: links are access-guarded (`MeetingLinkPolicy`) and never serialized into public props or logs

### 3.7 Reserved (Phase 5 sketch)

**`calendar_connections`** — ULID PK; `user_id` FK RESTRICT; `provider` varchar; token storage via **Laravel `encrypted` cast** columns (never plaintext — §9); `scopes` jsonb; `status` varchar; **UNIQUE (user_id, provider)**. Full design handled by its approved Phase 5 task.

## 4. Level-Decision Summary (master prompt §8 checklist)

| Item               | Decision                                                                                                                                                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PK strategy        | Domain tables `char(26)` ULID; starter `users` stays bigint — UUID/ULID-vs-bigint evaluation recorded in D-08 (ULID lexicographic sortability = good PostgreSQL index locality; UUIDv4's index fragmentation risk avoided) |
| FK deletion rules  | `users`/audit tables RESTRICT; content tables CASCADE; fiscal tables never deleted (status transitions instead)                                                                                                            |
| Unique constraints | `expert_profiles.username` + `expert_profiles.user_id`; `categories.slug`; `expert_categories` composite; `meeting_details.booking_id`; `bookings.hold_id`; partial uniques in payments/refunds/webhook_events             |
| Indexing           | Dashboard queries `(owner, starts_at)`; public partial indexes (`is_active`, `status='published'`); retry scans `(status, created_at)`; hold expiry partial indexes                                                        |
| Deletion policies  | See §5                                                                                                                                                                                                                     |
| Concurrency        | Holds + their EXCLUDE constraint; confirmed-booking EXCLUDE constraint; read-time hold expiry. **How the two EXCLUDE layers compose — proven on real PostgreSQL in 0.6 before finalizing**                                 |
| Sensitive data     | No raw card data anywhere; `calendar_connections` tokens are `encrypted`-cast only                                                                                                                                         |

## 5. Deletion-Policy Summary

| Table                                                                                      | Hard delete? | Policy                                                                               |
| ------------------------------------------------------------------------------------------ | ------------ | ------------------------------------------------------------------------------------ |
| `users`                                                                                    | **No** (MVP) | Account deletion anonymizes PII (POST-MVP evaluation) — that is why FKs are RESTRICT |
| `bookings`, `payments`, `refunds`, `financial_entries`, `booking_holds`, `meeting_details` | **No**       | State transitions only; immutable audit locks                                        |
| `availability_rules`, `availability_exceptions`, `expert_categories`                       | Yes          | Owner CASCADE; regenerable business data                                             |
| `services`, `expert_profiles`, `categories`                                                | No           | `is_active`/`status` gating; related rows RESTRICT                                   |
| `notifications`                                                                            | Yes          | Framework default                                                                    |
| `webhook_events`                                                                           | No           | Status lifecycle (received→processed/ignored/failed)                                 |

## 6. Simplification / Alternative Proposals (asked for by the prompt)

| ID  | Alternative                                                                               | Recommendation                                                                                                                                     |
| --- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1  | Merge `availability_exceptions` into `availability_rules` with a row-type discriminator   | **Rejected** — date vs weekday/time shapes mix differently; CHECKs and queries get muddier; two tables stay clearer for the cost of one table      |
| A2  | Merge `booking_holds` into `bookings` (status `pending_planned`)                          | **Rejected** — hold lifecycle (expiry, released holds, multiple users racing) pollutes booking identity and makes exclusion constraints ambiguous  |
| A3  | Replace typed `financial_entries` with a full double-entry ledger (debit/credit accounts) | **Not recommended for MVP** — typed rows with a sign reach the same bookkeeping while needing fewer ceremony; upgrade path documented for POST-MVP |
| A4  | `expert_profiles.languages` as separate `expert_languages` table                          | **Rejected** — jsonb suffices for a bounded list                                                                                                   |
| A5  | Single payments+refunds table with row type discrimination                                | **Rejected** — separate tables keep statuses/checks clean and partial unique indexes natural                                                       |

## 7. Acceptance Criteria

- ✅ All 16 tables from master prompt §8 covered; each with purpose, main columns, relations, PK, FK rules, unique constraints, indexes, deletion policy, and concurrency evaluation.
- ✅ ULID-vs-UUID-vs-bigint evaluated with PostgreSQL index effects (D-08 rationale + revisit trigger).
- ✅ Money stored as integer minor units; floating point prohibited; no raw card data; third-party credentials stored only via `encrypted` cast.
- ✅ Module ownership matches the approved 0.3 map (incl. the `booking_holds`→Scheduling shift, justified there).

## 8. Implementation Notes (not law, recorded constraints)

- PostgreSQL-specific constraints (EXCLUDE, expression index, CHECK conventions) mostly fit Laravel Schema Builder; raw `DB::statement()` migrations are used where needed — verified in task 0.6 and applied in Phase 1.2+.
- Migrations target PostgreSQL only (starter sqlite is scaffold default); the model does not claim SQLite compatibility (D-04: SQLite cannot validate this constraint set).
- Named constraints are used for CHECK/EXCLUDE where the builder supports them, to keep migrations reversible and documented.
- ULID PKs store as `char(26)` (Laravel `HasUlids` default); a future `uuid`-type storage optimization is explicitly out of MVP scope (documented revisit trigger).
